# Agent Team 2.0.0 Codex 行为 A/B

## 结论

这轮样本支持受控安装，但不支持“Agent Team 能让并行任务普遍提速”这个结论。

价值主要在调度抑制：两个很短、可以一次读取的独立来源，原生基线启动了两个子 Agent；候选保持主线程执行，结果一致，墙钟约减半，总 token 减少约 84%。真正值得拆分的双流审计中，两组都启动两个子 Agent，质量都达到预设 gold，候选耗时和 token 没有优势。

所以 2.0.0 的定位是薄治理，不是更强 Runtime：减少错误 spawn，固定 writer/reviewer 边界，并让主线程只做仲裁和必要抽验。

## 实验边界

- 基线与候选使用同一台机器、同一 Codex CLI、同一默认配置路径和同一只读夹具。
- 候选仅通过测试仓的 `.agents/skills/` 加载三个 Skill；没有安装到默认 Codex。
- 子 Agent 未指定模型和 reasoning effort，继承宿主设置。
- 每次都是新持久任务；没有复用旧任务证明新配置生效。
- 记录来自真实 rollout，不以 CLI 汇总输出猜测 spawn。
- 每个场景只有一组有效 A/B，只能证明本次行为，不能推导长期均值。

`codex exec --ephemeral` 样本 `01a03d33-6a96-7083-b408-a7be4c249e45` 被排除：Skill 发起原生 spawn 时，宿主返回 `no thread with id`。这是当前 CLI 的 thread 注册边界，不是正常多 Agent canary 环境。

## 结果

| 场景 | 基线 | 候选 | 结论 |
|---|---:|---:|---|
| 单值读取 | 0 spawn；45,323 token；9.95s | 0 spawn；45,272 token；11.49s | 行为与质量一致，无明显差异 |
| 两个短来源 | 2 spawn；289,421 token；44.03s | 0 spawn；45,711 token；21.85s | 候选避免误拆，token -84.2%，墙钟 -50.4% |
| 双流契约审计 | 2 spawn；517,078 token；90.51s | 2 spawn；525,563 token；95.67s | 都命中 A1、B3；候选无性能收益 |

token 是根线程与全部子线程 `total_tokens` 之和，包含缓存输入。墙钟按根 rollout 第一条和最后一条事件计算。

### 单值读取

- 基线：`01a03d34-3bc8-7b73-9360-715209c3f6b5`
- 候选：`01a03d3c-0154-7e22-8ddf-313b222acc75`
- 两组都直接读取 `note.md` 并返回 `release_channel=canary`，没有 spawn 或 wait。

### 两个短来源

- 基线根任务：`01a03d34-8b91-7022-ae1f-48d652239bc9`
- 基线子任务：`01a03d34-c159-7e71-9795-c50b967cf284`、`01a03d34-d240-7123-9255-a5aa3e53fec5`
- 候选：`01a03d35-5d69-7001-b534-61e90668c3a2`

两个文件各只有一条实质规则。基线仍创建两个 `explorer`，候选应用“能在一次 bounded read 内完成就留在主线程”的规则。两组最终都正确判断所有权互补、没有冲突。

这是本轮最清楚的正向证据：Agent Team 没有增加能力上限，而是降低原生调度的误触发成本。

### 双流契约审计

- 基线根任务：`01a03d36-cff9-75d2-8a6b-ccdafc3c46d3`
- 基线子任务：`01a03d37-27f6-7ea1-8804-637d5e647f8f`、`01a03d37-4572-7412-b4f9-8ed57cd96972`
- 最终候选根任务：`01a03d41-a104-7530-bc7d-1b549a58fadd`
- 最终候选子任务：`01a03d41-e767-7140-859f-5ee009910485`、`01a03d41-f8ba-79b1-acb4-754cefbb39a5`

预设 gold 是 A1 与 B3 两个局部缺陷，且不存在跨边界所有权冲突。两组都达到 gold。候选使用两个只读 `explorer`，根线程只读取 `integration.md`，收到 handoff 后再对关键行做窄抽验。

中间候选 trace 发现两个合同问题，并已进入 2.0.0：

1. spawn 默认继承完整父会话，和“最小 Task Request”不一致；现改为 `fork_turns: "none"`，模型仍继承。
2. `wait_agent` 在收到进度 `MESSAGE` 时也会返回；现只把 `FINAL_ANSWER` 或明确 completed 当作 join，避免主线程因中间消息重做完整分支。

最终候选在这个场景没有提速：比基线多约 1.6% token、慢约 5.7%。这说明真正并行时，Skill 的协调成本没有被样本证明能带来性能收益。

## 发布判断

允许安装 2.0.0，理由是：

- 简单任务和短来源没有新增 spawn；短来源误拆显著减少。
- 真正独立的审计仍能使用 Codex 原生并行，预设质量 gold 未下降。
- 包内没有 Claude 生命周期、自定义 Agent、固定模型、Hook 或第二 Runtime。
- 安装是固定版本候选包，可移除 marketplace 回滚。

安装后的结论仍应写成“受控试用”。至少积累更多真实任务后，才判断是否默认长期启用。后续主要观察 false-positive spawn、父子重复读取、writer 写域冲突、review 快照漂移和总 token；不先扩展 Dynamic Workflow。
