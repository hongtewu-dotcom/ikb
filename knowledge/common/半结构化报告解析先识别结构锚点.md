## 是什么／怎么做

解析 Markdown 或其他半结构化技术报告时，先用标题、表头和分隔行确定结构，再解析数据内容。表格列数和格式版本从表头判断，不能按数据行的分隔符数量推断，因为 JSON、代码或自由文本本身可能含有 `|`。一张表属于哪个章节，应从表格位置向前找最近的标题，不能用跨标题的宽泛正则把后面的第一张表归给前一章节。

同一份 Markdown 既给人阅读又要被机器无损回读时，结构化对象保留一个带类型的 JSON 块作为机器合同，人读小节由它渲染。不能靠标题中文名反推原字段：旧实现把五个字段渲染成小节后，只能读回一段 `_raw_md`，字段边界全部丢失；加入 JSON 块并优先解析后，五个字段才完成往返一致。两种表示若由不同写入路径维护，会重新产生双真源。

提取代码差异时，再按当前生成器合同过滤框架生成字段，只保留业务字段；例如 Thrift 生成的 `magicNumber`、`__isset_bitfield` 不应进入业务字段变更。过滤规则要以当前语言和生成器为准，不能把历史字段清单当作永久协议。

批量改写源码或脚本时也先用方法、循环体和变量作用域定位目标，不能因同名方法多次出现就做全局文本替换，也不能依赖可能乱码的中文注释作唯一锚点。遇到统一编码错乱，先在小样本验证可逆的逐层解码；不能稳定还原的行按代码上下文人工修复，避免继续扩大损坏。

生产者引入新的类型化引用时，转换器、校验器和后续重写入口必须同时升级。历史案例把 `文件:E1` 误当普通路径，导致生成 Agent 临场改格式；修复不是截掉后缀，而是打开绑定的结构化产物、按类型展开引用并生成确定性索引。测试还要继续穿过会再次写入同一状态的 Dispatcher 等最终消费者，并使用真实运行时事件形态，不能手工构造一个已经正确的中间产物。

引用标记允许附带章节定位或多个来源时，先识别完整方括号，再从括号内容中提取全部合法 ID；不能只把正则放宽到第一个 ID，否则会漏掉同括号后的来源，也可能接受缺右括号的残缺输入。新内容采用一个来源一个标记的规范写法，解析器兼容存量组合格式，并为单来源、带定位、多来源和 malformed 输入各留一个回归样例。

工具结果可能是由空白分隔的多个完整 JSON 值，例如 telemetry 后紧跟业务查询结果。解析器应按 JSON 值边界顺序解码，再从完整对象中选择目标协议；只调用一次 `json.loads` 会丢掉合法结果，从任意日志文本中搜索花括号又会误收残片。只接受完整值和允许的分隔符，业务字段门禁保持不变。

标识符和 locator 解析必须保留原始语义。`S032` 这类 ID 是字符串，不能转整数后变成 `S32`；范围归一化也要保留端点宽度。Markdown locator 的 `#fragment` 是章节定位，检查文件存在性时可暂时剥离 fragment，但不能改写持久化 locator，也不能影响专用 selector 的格式校验。

## 什么时候用

实现或修复 Markdown 报告解析、表格版本识别、章节归属，从生成代码中提取业务字段变化，或编写需要精确定位源码上下文的批量改写脚本时使用。

## 什么时候别信

来源包含旧版接口变更报告、一轮 2026-08 的 PRD 证据链事故和旧知识系统的 Markdown 往返修复。当前报告语法、引用类型、生成器版本和业务字段合同优先；结构已有正式 AST、Schema 或解析库时直接复用，不退回正则拼接。历史本地修复与测试不证明当前线上流程已通过。
