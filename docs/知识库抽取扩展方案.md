# IKB 知识抽取扩展方案

## 结论

IKB 不再按“每篇来源生成一张总结卡”运行。`individualbusinesleisure` 和 `traffic-kb` 的可用部分要合并进 IKB：

- 用 **领域问题集 + Gap + 证据资格** 控制“还缺什么、哪些结论能成立”；
- 用 **术语、领域、实体、流程、入口、服务事实和评测案例** 让知识可以被检索、定位和执行；
- 用 **Source → Evidence/Episode → Knowledge → Task 输出** 保留原文，不让抽象替代事实。

因此，一篇有业务结构的文档可能产出多个互相链接的知识对象，也可能只进入 Source 和 Gap，不强行产出 Knowledge。

## 吸收边界

| 来源项目 | 吸收的能力 | 不吸收 |
| --- | --- | --- |
| `individualbusinesleisure` | 领域 Profile、问题集、Gap backlog、来源生命周期、事实资格、历史/当前/规划分层、完整性/逻辑性/正确性门禁 | 其固定商业方向、业务内容、目录内的公司知识和 PRD 模板 |
| `traffic-kb` | glossary、domain、entity、flow、frontend-map、service-card、data-access、入口/链路双索引、评测 case、增量失效和人审 pending | 其机票/火车业务事实、代码仓运行时、远程服务和部署方式 |

## IKB 的目标知识产品

### 1. 领域包（Domain Pack）

回答“这个业务是什么、边界在哪里、缺什么”。每个领域包至少包含：

- `domain_profile`：业务目标、范围、owner、上下游域、当前/历史/规划状态；
- `glossary`：业务名、别名、代码名、易混淆概念和反例；
- `strategies`：目标、策略、指标、约束和止损条件；
- `gaps`：问题、影响、缺失证据、下一次取证任务、状态；
- `related_sources`：每一项的来源与有效时间。

消费者：需求澄清、向上沟通、方案背景、任务总管。

### 2. 业务实体包（Entity Card）

回答“对象是什么、由谁生产、谁消费、状态如何走”。不要只写对象名称，至少抽取：

| 字段 | 内容 |
| --- | --- |
| 定义/别名 | 业务名、代码名、同名异义、禁止混用项 |
| 关键字段 | 字段名、语义、枚举、单位、来源、是否可空 |
| 关系 | 关联实体、主/子单、产品/订单/履约单元等关系 |
| 生命周期 | 创建、更新、冻结、履约、取消、退款、归档等状态 |
| 生产/消费 | 服务、仓库、页面、任务、消息和数据表 |
| 不变量 | 必须成立的关系、金额/数量/身份/时间边界 |
| 例外 | 降级、历史兼容、人工兜底、无法判断的字段 |
| 验证 | 代码/接口/数据/日志/测试入口 |

消费者：编码、CR、数据核对、按对象影响分析。

### 3. 业务流程包（Flow Card）

回答“从哪里进、经过哪些节点、每个节点做什么、改动边界是什么”。至少抽取：

```text
触发条件 → 业务入口 → 页面/HTTP/RPC/任务 → 服务节点 → RPC/MQ/DB 边
        → 状态/结果 → 异常分支 → 恢复/补偿 → 观测和验收
```

每个节点都要分别记录：入口锚点、仓库/服务、职责、主要输入输出、下游、允许改动范围和明确不改范围。架构图只作为证据，不能替代节点表。

消费者：PRD → 工程方案、跨仓 Spec、代码定位、排查和评审。

### 4. 代码事实包（Service/Data/Entry Facts）

能从代码图谱或仓库确定性得到的内容，不让模型自由总结：

- 页面/Bundle → HTTP 路径 → Controller → RPC/Thrift → 服务/仓库；
- Thrift/HTTP/MQ/Crane 定时任务入口；
- 关键方法、文件、类、调用方、被调用方；
- 字段读写者、表/缓存/Topic、生产者/消费者；
- 跨仓契约、调用方向、版本或 commit；
- 代码变更触发的 stale 信号。

这层是 `traffic-kb` 的 facts，不与业务语义混在一张卡里。代码能直接派生的事实进入事实包；业务含义、不变量和改动建议进入语义包，并互相引用。

消费者：编码 Agent、CR Agent、跨仓影响分析、入口检索。

### 5. 执行、排查与决策包

把“理解”转成可执行动作：

- `playbook`：输入、前置条件、步骤、检查点、分支、告警、回滚、停止条件、产出物；
- `decision`：问题、选项、选择、理由、放弃方案、影响、owner、时间和当前/规划状态；
- `lesson`：事件、影响、根因、暴露缺口、修复、回归、复发信号；
- `test/eval case`：问题、输入、期望召回/判断、真值来源、通过标准和结果。

没有真实入口、阈值或恢复证据时，写 `unknown`/`blocked` 和下一次取证任务，不能编命令或把规划写成已上线。

消费者：测试、排查、评审、任务执行、Harness 评估。

### 6. 任务输出包

知识库不是终点。基于上面五类知识，Agent 应能生成并保留：

- PRD/技术方案的业务背景、范围、链路和未决项；
- 跨仓 Spec 的仓清单、节点职责、协议和实施顺序；
- CR 检查表：不变量、边界、兼容、测试和回滚；
- 排查单：现象—输入—链路—证据—结论—恢复；
- 沟通包：结论、依据、风险、选项、需要对方决策的事项；
- 本地 Issue：Gap、证据缺口、验证任务和下一步 owner。

输出包必须回链到 Knowledge 和 Source，不能成为没有消费者的另一个知识副本。

## 人物包也要扩展，但单独治理

人物不按消息数建档，也不每条消息重建。每次 intake checkpoint 或每日 evidence-view 重建证据视图，按周或达到增量门槛才做蒸馏。人物包至少包含：

- 身份证据和有效时间；
- 独立 Episode、负责的领域/决策/交付；
- 反复出现的决策标准、风险约束、承诺和 owner；
- 写作结构、证据摆放和修改习惯（必须有署名文档或被采纳的修改）；
- 可复用工作能力，必须写清输入、输出、任务场景和能力边界；
- 协作契约：准备什么输入、用什么格式交付、节奏和升级方式；
- 冲突、过期、unknown。

身份归因、重复性和行动价值不满足门禁时，只留 Evidence/Episode，不写人物 Knowledge。

### 人物的多视角抽取器

人物不是一张“性格画像”，而是多个可独立成立、可独立失效的工作视图。每个视图单独统计 Episode、时间范围、证据来源和置信度；不能用一个视图的证据替代另一个视图。

| 视图 | 具体抽什么 | 可产生的工作用途 | 最低证据要求 |
| --- | --- | --- | --- |
| 身份与职责 | MIS/UID/别名、署名、明确 owner、负责领域/交付 | 判断是否能把材料归给此人、找谁确认 | 精确身份匹配；署名/owner 证据 |
| 领域与问题版图 | 反复出现的业务域、系统、项目、问题类型 | 任务分派、上下文预加载 | ≥2 个独立 Episode |
| 决策标准 | 明确要求保护/衡量/避免的条件、证据和边界 | 方案评审、向上汇报、决策准备 | ≥2 个直接决策/评论 Episode |
| 风险与质量门槛 | 对数据、回滚、兼容、上线、资金或范围的反复要求 | CR 检查表、风险预警 | ≥2 个直接要求或采纳的修改 |
| 写作结构 | 标题层级、先结论/先证据、现状-方案-边界、未知项、修改习惯 | 模仿其可接受的文档结构 | ≥2 篇署名文档或被采纳修改 |
| 评审行为 | 关注的文件/逻辑、评论位置、阻断条件、接受/拒绝理由 | 生成 CR 预检表、准备评审材料 | ≥2 次可追溯评论及处理结果 |
| 沟通契约 | 需要什么输入、偏好的交付形态、更新节奏、升级路径 | 大象沟通、向上管理、跨团队协作 | ≥2 次相似交互且结果可见 |
| 执行与闭环 | 如何拆任务、确认 owner、追踪 TODO、处理阻断、验证收口 | 任务总管和跟进提醒 | ≥2 个有结果的任务 Episode |
| 可复用能力 | 输入→动作→输出→任务结果→适用边界 | Agent Skill/Workflow 的候选 | ≥2 个相似任务且结果/产物可核验 |
| 协作网络 | 明确的上下游、共同 owner、交接关系和升级对象 | 交接路径、沟通对象选择 | 只能记录显式关系；不得从群共现推断 |
| 时间变化 | 新旧标准、职责变化、已废弃偏好、冲突观点 | 避免把历史标准当当前标准 | 至少两个时间点；保留 superseded |
| 未知与反例 | 一次性发言、未采纳建议、冲突、身份歧义 | 防止过拟合和错误画像 | 只需证据定位，不得强行归纳 |

每个候选观察必须落成以下结构，而不是形容词：

```yaml
person_observation:
  view: decision_criteria|risk_bar|writing_pattern|review_behavior|communication_contract|capability|...
  pattern: "可观察的重复行为或工作要求"
  episodes: ["Episode/record 引用"]
  trigger: "什么任务/场景下出现"
  response_shape: "对方实际要求或采用的交付方式"
  usable_for: "下一次 Agent 如何使用"
  boundary: "不适用、未知或不能推断什么"
  temporal_state: current|historical|superseded|conflicted|unknown
  confidence: low|medium|high
```

“架构能力强”“沟通很好”“比较严格”不能直接入库；必须改写成可验证的行为模式，例如“在两次架构评审中先要求补齐入口、证据和不改边界，再讨论实现方案”，并保留两次独立引用。

## 类型分流：不同知识使用不同抽取器

IKB 的 Analyst 先判定 `extraction_mode`，再使用对应方法；不允许用人物抽取器分析业务，也不允许用业务摘要器生成 Skill。

| `extraction_mode` | 主要抽取方法 | 重点产物 | 准入门槛 |
| --- | --- | --- | --- |
| `fact/concept` | 定义、别名、字段/枚举、来源版本、反例和冲突比对 | 可引用事实卡/术语卡 | 直接证据；时效边界清楚 |
| `entity` | 关系图、生产/消费、生命周期、状态机、不变量 | Entity Card | 对象关系和至少一个验证入口 |
| `flow/entry` | 入口识别、节点-边遍历、状态/异常/补偿、前后端映射 | Flow Card + Entry Index | 入口锚点或明确 blocked |
| `service/data_fact` | 代码/图谱确定性抽取、字段读写、契约和 commit | Service/Data Fact | 可复现代码或图谱来源 |
| `decision` | 背景→问题→选项→标准→选择→替代方案→影响→状态 | Decision Card | 明确决策或明确标 planned/unknown |
| `playbook` | 前置条件→步骤→检查→分支→观测→回滚→停止 | 执行/排查卡 | 步骤和验证证据足够复现 |
| `lesson` | 时间线→影响→根因→缺口→修复→回归→复发信号 | Lesson Card | 事故事实和修复/验证状态分开 |
| `goal/project` | 目标→指标→里程碑→owner→依赖→状态→决策点 | Project/Goal Card | 明确时间和状态；计划不冒充事实 |
| `review/writing` | 原稿→评论→采纳/拒绝→修改→最终稿→效果 | Review/Style Card | 有版本、作者、评论和处理结果 |
| `agent/experience` | 目标→失败/阻断→纠偏→Verifier→Artifact→结果→反馈 | Experience Record / Pattern | 先 triage；重复模式后才候选 |
| `person` | 多视角 Episode 聚合、时间比较、身份/重复/行动门禁 | Person Evidence View / Person Card | 身份精确、至少两个独立 Episode、可改变协作 |
| `synthesis` | 多来源对齐、共同模式、分歧、适用范围和反例 | Synthesis Card | 多批次/多任务复现，不能单篇横评直接泛化 |

同一来源可以同时进入多个抽取器，但每个产物必须保留自己的证据链。例如一篇评审文档可以同时产生协议事实、评审行为证据和一个待验证的 Playbook；不能把三者拼成一句“评审很严格”。

## 从一篇来源到知识产品的抽取清单

Analyst 逐篇先判断来源包含哪些模块，再按模块抽取；不要求每篇都有全部模块：

| 来源内容 | 应抽取 | 不能用什么替代 |
| --- | --- | --- |
| 业务介绍/策略 | 目标、对象、边界、指标、策略、风险、止损 | “收入重要”“要标准化” |
| 产品/协议 | 字段、枚举、输入输出、对象关系、兼容和迁移 | 一句“协议分层” |
| 架构图/链路说明 | 入口、节点、边、职责、状态、改动/不改边界 | 一句“存在调用关系” |
| SOP/故障复盘 | 现象、条件、步骤、分支、证据、恢复、复发信号 | 只摘根因或配置值 |
| 评审/评论 | 问题、原建议、采纳/拒绝、原因、验证结果 | 只保留最终文案 |
| Agent 会话 | 目标、失败、纠偏、Verifier、Artifact、反馈、非显然修复 | 完整 tool output 摘要 |
| 规划/路线图 | 当前、历史、规划、依赖、里程碑和未决决策 | 把规划当线上事实 |
| 人物对话/署名文档 | 直接证据、决策标准、写作/沟通结构、协作契约 | 人格或能力评分 |

## 质量门禁

一条知识进入 `draft` 前，必须回答：

1. 它是事实、语义、流程、执行方法、决策、经验还是人物观察？
2. Agent 下一次具体用它做什么？输入、输出和停止条件是什么？
3. 能否打开来源定位到原句、表格、字段、入口、代码或验证结果？
4. 当前、历史、规划、推断和未知是否分开？
5. 是否重复、冲突、过期，或只是一次性信息？
6. 缺什么证据；下一次取证或真实 Task 怎样验证？

没有可执行消费者的抽象句不入 Vault；有证据但尚未验证的内容进入带边界的 `draft`，不是直接 `verified`。

## 当前 IKB 的改造顺序

1. 先保留现有 Source 和已建立的卡片，不删除历史；将同一业务来源重编译为 Domain/Entity/Flow/Entry/Playbook/Decision/Gap 多层包。
2. 优先重跑已有交通高价值文档：协议、架构、前后端入口、辅营、故障复盘、仓库 Ready、AI 自动化；每篇先出完整事实包，再拆短入口卡。
3. 为每个高价值领域补一组可执行评测案例，验证“用户故事 → 业务概念 → 入口/链路 → 仓/方法 → 检查表”的召回和判断。
4. 每次批次完成后更新 Gap 和 stale 状态；已有结论只做 revision/retire，不静默覆盖。
5. 只有知识被真实 Task 使用并通过验证，或用户明确确认，才从 `draft` 升级 `verified`。

本文件是抽取目标，不是业务事实；业务事实仍只来自 IKB Source 和带引用的 Knowledge。
