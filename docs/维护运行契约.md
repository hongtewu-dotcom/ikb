# IKB 维护 Run 契约（旧流程兼容说明）

> 2026-08-27 起，默认维护入口已经切换为 `source-sync / semantic-maintenance / weekly-housekeeping`。它们分别只写一份 `ikb-receipt.v1`，不再创建下文的 Task/Run/Plan/Artifact/QV5 硬链。下文只用于读取历史 Run、排障旧入口和保留既有测试，不是当前维护主合同。

当前职责边界：

- `source-sync` 每 6 小时增量保存本地 Source、刷新 Inbox，并在局部失败时继续独立步骤，最后写一份 Receipt；不生产 Knowledge。
- `semantic-maintenance` 每天由 Codex automation 从 Inbox 选择最多三个主题；普通 Knowledge 才能按证据作 new/update/keep/retire，Principle 只能生成待确认 diff。
- `weekly-housekeeping` 每周一 03:30 生成覆盖与整理快照，只写一份 Receipt，不修改 Knowledge。
- `scripts/ikb-maintenance.mjs daily|weekly` 只保留为显式 legacy compatibility，不被已安装写任务调用。

旧 `daily / weekly` 维护不是一组互不相干的 CLI 命令。显式运行 legacy 入口时，`scripts/ikb-maintenance.mjs` 会为每次维护创建一个 Task 和一个 `ikb-harness` Run，把每个步骤的输入依赖、输出 Artifact、角色交接、门禁和最终验收写入同一条事件账本。

## 固定链路

```text
home-init
  → local-memory-sync → registered-files-sync
  → source-ingest → agent-team-observe → source-raw-dedup
  → experience-triage
  → candidate-discover → candidate-resolve
  → source-coverage
  → people-rebuild
  → knowledge-rebuild → knowledge-archive → knowledge-lint
  → reasoning → doctor → ledger → report
  → maintenance-summary（冻结的执行摘要 Artifact）
  → Verifier + ikb-run-quality Eval
  → Run succeeded / failed
```

历史 Run 的 `harness repair` 不在这条链上。它是独立的 Outer Loop 运维动作，必须显式执行并单独生成 Run/Artifact；日常知识维护不会因为历史 Run 尚未修复而阻塞，也不会隐式消耗学城读取额度。

`agent-team-observe` 只读消费 Codex rollout，按 turn 汇总 Agent Team 2.0.0 的安装身份、根子线程 token、墙钟和原生协作调用。该步骤显式使用 `--fail-open`：采集不可用时写入 unavailable 和 reason code，仍生成紧凑 Artifact；它不是知识维护门禁，也不会向 Codex 注册 Hook。

## 语义知识生产边界

上述固定链路当前负责增量接入、去重、Triage、候选解析、人物证据投影、现有 Knowledge 索引与质量巡检。它会把值得分析的内容送入队列，但不会在一个确定性脚本中自由发挥语义抽取，也不会把 Triage 命中直接写成 Knowledge。因而“daily 维护成功”只证明输入与治理链健康，不能证明本轮已经新增或修订正式知识。

正式语义消费必须另起有边界的 Analyst/Curator Run，并经过：

```text
冻结 Source
  → 来源结构清单
  → Evidence 与参考事实
  → 类型化 Fact Package / Product View
  → 信息损耗重新计算
  → QV5 完整评审稿
  → 用户确认或真实任务验证
  → revision transaction
```

每日维护后续只负责按优先级和背压创建这类待执行 Run；Agent 负责语义判断，Core 负责逐单元处置、双向引用、事实召回、主张支持、问题覆盖、唯一 `canonical_key`、完整正文一致性和 revision 幂等。没有 V3 manifest/result/fidelity Artifact 的新正式 Knowledge 不能进入新的评审包。旧 QV4 draft 继续可读，但维护成功不会自动把它升级为 QV5。

每个步骤都必须有前置步骤完成；前置步骤失败时，后续步骤为 `blocked`，不会继续读、写或伪装成成功。每个成功步骤至少产生一个 `maintenance-step` Artifact，并写入：

- `run.step_started` / `run.step_finished`
- `run.handoff`：`ikb-harness` → 实际责任角色，带输入/输出引用
- `run.gate_evaluated`
- `run.artifact_linked`

Run 启动后必须通过 `./bin/ikb run plan <run-id> --file <plan.json>` 登记上述 DAG；Core 会校验步骤唯一、依赖存在且无环，并在首个步骤事件出现后冻结计划。Store 创建的空计划不能作为执行计划使用，也不能由脚本直接改写来绕过校验。`maintenance-summary` 也是正式计划步骤：它在 Eval 前生成、注册、关联并冻结，Verifier 覆盖它以后才执行质量评估。Eval 后只更新 `ikb-data/maintenance/runs/` 下的人类观测投影，不再向已评估 Run 追加普通 Artifact，避免二次评估发生 Artifact 覆盖漂移。

每个 `maintenance-step` Artifact 只保存该步骤的紧凑契约结果，例如扫描数、增量数、问题数、报告 ID 和门禁结论，不复制完整 doctor、`people rebuild`、`source ingest` 输出、Source 正文或候选正文。完整状态仍由 Source Registry、Knowledge Vault、Ledger 和治理账提供；维护 Artifact 只负责证明“本步消费了什么、产生了什么结论”，避免日常运行反复制造几十 MB 的重复投影。`source-coverage` 位于候选解析之后，确保本轮新接入的学城 Source 也进入同一轮覆盖账。

最终只有同时具备以下条件才把 Run 标为成功：

1. 所有步骤成功；
2. `doctor` 和 `ledger verify` 通过；
3. 有维护摘要 Artifact；
4. Verifier 结果为 `pass`；
5. `ikb-run-quality` 真实 Run 评估的 8 个 Case 全部通过；它读取本次 Run 的事件、Plan、Artifact 和 Approval，不读取另一个合成回放。

`terminal=succeeded` 仍不等于质量通过。观测页读取 `run-quality` 投影；缺 Verifier、Evaluation、Gate 或 Artifact 时会显示 `quality=block`。

## 可追溯入口

```bash
./bin/ikb run plan <run-id> --file <plan.json>
./bin/ikb run show <run-id> --json
./bin/ikb timeline <task-id> --json
./bin/ikb observe daily --json
```

当前维护摘要写在 `ikb-data/.system/maintenance/`；Task、Run、Artifact、交接和门禁的兼容账本位于 `ikb-data/.system/ledger/events.jsonl`，Run 位于 `.system/runs/`。旧 20 步 runner 生成的 `ikb-data/maintenance/runs/` 只作历史兼容。真实 Source、Knowledge 和公司数据继续留在被 `.gitignore` 排除的 `ikb-data/`，不上传 GitHub。

## 故障处理

失败只会得到 `Run failed` 和 `Task waiting`，原始步骤、错误、Artifact 和下一步保留。修复后重新执行维护，产生新的 Run；不覆盖旧 Run，也不把失败状态改写成成功。
