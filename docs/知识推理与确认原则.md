# 知识推理与确认原则

## 结论

IKB 不应把每个输入或每个 Draft 都变成用户确认项。正确顺序是：

```text
Source / Experience
  → 证据归并与时间/冲突判断
  → 当前 Knowledge 对照
  → 全局推理与确认项压缩
  → advisory draft / defer_until_task / ask_user
  → 必要时才进入用户确认
```

“已导入”只说明材料被安全保存；“已 Triage”只说明会话命中了分析信号；“已分析”才说明形成了带事实、推断、未知和边界的分析 Artifact；“已 verified”还必须有真实 Task 验证或用户确认。

## 一、四种判断不能混在一起

### 1. 事实

能直接回到 Source、代码、配置、运行 Artifact 或明确账本事件。事实要保留时间和来源，不因新表述出现就静默覆盖。

### 2. 推断

由多个事实归并出的可复用模式。推断必须写出证据链、适用范围和推断边界，不能伪装成原文事实。

### 3. 未知/冲突

缺少当前证据、来源之间互相矛盾或规划状态未落地时，保留 `unknown/conflicted`。未知不是失败，也不是让用户立刻补答案的理由；只有具体 Task 需要该信息时，才启动取证。

### 4. 决策

会改变默认行为、门禁、权限、Approval、敏感字段处理或人物使用方式的事项。当前证据不能推出时，才交给用户。

## 二、系统自动处理什么

以下规则已经由用户和系统边界明确，可以自动采用，不重复确认：

- 案例数字只作为案例，不直接变成业务阈值；
- 规划、建议和当前线上事实分开；
- 没有长期复用价值的文档可以 `skip`；
- 工作 Knowledge 和个人 Knowledge 分域保存；
- 公司/工作原始材料只留在本机 `ikb-data/`，不进入 GitHub；
- 默认只生成本地草稿，不发送大象消息、不发表评论、不改学城文档；
- 敏感字段按最小披露处理，未明确授权不扩写账号、代理商、金额拆分；
- Draft 只能作为 advisory 使用，不能自动升级为 verified；
- 生成路由表、证据清单和排查草稿属于本地低风险动作，外部写入仍需 Approval。

自动处理只改变推理报告中的处置，不修改 Knowledge 生命周期，也不删除待审计的原始问题。

## 三、什么应该延后到具体 Task

以下问题不是原则决策，而是当前证据缺口：

- 最新配置、SOP、日志、观测和测试数据入口；
- 当前仓库、服务目录、流量路径和历史任务；
- 真实演练、回归报告和当前上线状态；
- 第一次使用后的人工修订和 Task 验收结果。

它们进入 `defer_until_task`，由具体 Task 的取证和验证闭环解决，不在知识抽取阶段向用户泛问。

## 四、必须让用户确认什么

只有下列事项进入 `ask_user`：

1. **人物**：身份是否准确、观察是否可重复、适用范围是什么、是否允许 Agent 用于个性化准备；
2. **高风险规则**：哪些缺口必须阻断、哪些配置变更必须 Approval、Ready 结果如何影响治理；
3. **组织策略与副作用**：是否创建外部 Issue、发布评论/文档、采用生产阈值或改变权限边界；
4. **不可从证据推出的选择**：存在互相冲突的正式来源，且不同选择会导致不同执行路径。

用户确认的是“规则和授权”，不是让用户替系统重新阅读全部输入。确认后生成修订 Artifact 或 Approval 记录，仍不能绕过真实验证。

## 五、人物与普通知识采用不同门槛

普通业务 Playbook 有稳定证据和明确边界时，可以先以 medium draft 服务下一次任务；人物知识必须同时满足：

- 身份精确匹配；
- 核心证据来自直接发言或明确署名；
- 同一观察跨至少两个独立 Episode；
- 观察会改变后续工作准备；
- 不推断人格、动机、能力或私生活。

因此人物 `ask_user` 数量少不是系统漏提取，而是主动避免把群上下文或一次性话语当成画像。

## 六、运行产物与观测

`ikb reasoning run --scope work` 读取当前 Scope 的 Source、Experience、候选池和非 retired Knowledge，输出：

- `auto_resolved`：按系统原则自动处理；
- `defer_until_task`：留作未来取证/验证；
- `ask_user`：压缩后的真正决策队列；
- 原则判断、输入覆盖、指纹和账本事件。

报告落在 `ikb-data/governance/<scope>/reasoning/`，不写入 Vault。HTML 观测页只显示计数和决策队列摘要，不展示聊天全文。

## 七、成功标准

不以 Knowledge 数量、确认问题数量或 Experience 数量作为成功指标。每轮应能回答：

1. 哪些输入只是保存了，哪些已经深读；
2. 哪些结论来自事实，哪些是推断，哪些仍未知；
3. 哪些问题系统已经按边界处理；
4. 哪些问题需要具体 Task 取证；
5. 哪些问题确实需要用户决定；
6. 用户决定后，后续执行和验证是否改善。
